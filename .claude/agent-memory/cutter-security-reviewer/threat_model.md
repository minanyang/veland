The main boundary is the Claude Code permission system: skills declare `allowed-tools` (e.g. `Bash(cutter-land *)`), so anything a granted wrapper can do runs without a prompt. Wrappers take only an id/slug and build argv from origin, config and files under `.cutter/`.

**Why:** a grant on raw `gh`/`glab`/`git push` could be stretched into merge, force-push, or a different repo; the wrappers exist to stop that.

**How to apply:** when reviewing a wrapper, check (1) argv can't take flags from input, (2) repo/host stays pinned to origin, (3) which file paths it reads. Content the agent writes into `.cutter/` (PR body, issue draft) is agent-controlled. Prompt-injected text from issues or code can reach a published PR or issue unless something else gates it (a Write prompt, the user's approval). An `allowed-tools` prefix like `cutter-land *` covers every subcommand, including ones meant for other skills.

`cutter-land pr` (PR/MR create/edit) is granted in close and does not prompt. Since gh-55, `cutter-land check` (pr/pr-merge, github.com) makes a read-only pinned `gh pr view` and prints `pr: <STATE> <url>`; `pr: MERGED` sends close to cleanup without verify, which is safe only because `cutter-worktree rm` keeps a branch whose changes are not on the base (that check is the boundary, not the PR state). Since gh-35 (2026-10), `cutter-land issue` and `cutter-land comment` are deliberately NOT granted (public writes always prompt; `tests/skills.test.sh` fails on any grant in any skill that covers them, bare `Bash` included). The issue-draft content checks in `cutter-land issue` are quality gates, not a security boundary. Repo pinning comes from parsing origin's URL in `origin_parts`, so check any change to that parser.

Since gh-51, `work` grants raw read-only CLIs for `## Overlap`: `Bash(git fetch)` exact (docs: a rule with no `*` matches one exact command, so `--upload-pack=<cmd>` is not covered; never accept `git fetch *`), `gh pr list *`, `glab mr list *` (no write/file flags; `-R` can read another repo, accepted as read-only). `cutter-land issue` now `rm -f`s the draft after a successful create (need_file-checked path; the command always prompts).

`cutter-ticket --out` (#25, granted via `cutter-ticket *`) writes only `.cutter/gh-<n>/ticket.md`. `.git/info/exclude` does not stop a cloned repo from tracking `.cutter/...` symlinks, so check every path component of a pre-approved write, not only the leaf. That includes rename destinations: `mv -f a b` follows a symlink-to-dir `b` on macOS (verified in gh-24), so `need_file` on the source alone doesn't keep it inside `.cutter/`. Since gh-54, open grants exact `Bash(cutter-ticket issue-types)` (no args): a constant GraphQL query via `gh api --hostname github.com graphql`, owner/repo from `originRepo` as `-f` vars (`-f` never reads `@file`, unlike `-F`); read-only, also covered by work's `cutter-ticket *`. Repo-controlled `.claude/cutter.json` (incl. a worktree's, which the agent edits) only tunes the context gate, which is a cost control and not a security boundary. Since gh-56, `cutter-plan-check` also reads `.cutter/<id>/cold-read.md` (lstat leaf + non-blank, content never printed): an agent-writable process gate like evidence.md, not a security boundary.

Claude Code matches allow rules per subcommand (split on `&& || ; | |& &` newline) after stripping wrappers (`timeout`, `time`, `nice`, `nohup`, `stdbuf`, `command`, `builtin`, `noglob`, bare `xargs`, known-safe `VAR=` prefixes); redirect targets get a separate Edit/working-dir check. gh-22 tried a text guard rule ("a cutter script runs alone") and withdrew it (f008fb7): a probe of the engine's `tool.check` showed `cutter-x … > f`, `>f cutter-x …` and `ls; cutter-x …` already get `ask`, not `allow`, under `Bash(cutter-x *)`. The engine, not guard-bash.sh, is the boundary for stretched grants; don't re-request a text rule unless a new probe shows an `allow`.

Since gh-36, `hooks/stop-gate.js` (UserPromptSubmit/PostToolUse/Stop/SubagentStop) writes `.cutter/.sessions/<sid>.json` and `.cutter/<id>/session` with SID/ID regexes and lstat symlink checks; it is a process gate (agent can edit evidence.md), fails open, blocks once per stop. `cutter-review-packet`'s `security review: required` line is a routing heuristic, not a boundary: since gh-46 it fires on a file a granted `bin/` script or a registered hook loads one level deep by a static `source "$(dirname …)/…"` or a relative `require` (`scripts/lib.sh` holds `check_id`; `scripts/md-check.js` is loaded by `stop-gate.js`), not on dynamic paths, deeper loads or paths passed to `node -e`. It also fires on `skills/*/SKILL.md` and `agents/*.md` frontmatter hunks (254fbf2). Since gh-42, both packets drop `.claude/agent-memory` (exact pathspec, root only) from the diff but list every commit touching it with paths (`## Agent memory`); the control for memory *content* is work Step 8 showing the user the branch-wide memory diff before `/cutter:close` pushes it, not a reviewer.

Since gh-53, `hooks/grant.js` (UserPromptSubmit + PreToolUse Bash) snapshots a typed flow skill's `Bash(...)` grants into `${CLAUDE_PLUGIN_DATA}/sessions/<sid>.json` and returns `allow` for metachar-free commands for the rest of the session (no expiry, survives `--resume`; cutter-script grants bound to the typed ticket id since c3574a6, `ID_WORD` positions match each script's `check_id` argument). The flow skills are `disable-model-invocation: true`, so the trust question is "can the model make a prompt that starts with `/cutter:<skill>` reach UserPromptSubmit?". `CronCreate` needs no permission and its fired prompt is injected into the session (docs: a non-model-invocable skill "reaches Claude as plain text"); UPS input has no origin field, so 5205825 closes the cron path by recording grants as *pending* and confirming only when the transcript line with that `promptId` is `origin.kind: "human"` with `<command-name>/cutter:<skill>` (undocumented format, so a format change fails closed). Hook `allow` does not override settings deny/ask rules, guard `deny` wins (precedence deny > defer > ask > allow), plan mode excluded; whether `allow` skips the auto-mode classifier is undocumented (docs fetched 2026-10-18). `agent_id` is documented as present inside subagents and in-process teammates. Residual risk flagged in gh-53 review: `cutter-verify *` / `cutter-red-proof *` run `bash -c` on agent-editable worktree config/tests, so session-wide grants make edit→exec unprompted for the whole session (user accepted; AC6 binds them to the typed ticket). Since 41c5083 the confirm requires content to `startsWith("<command-message>cutter:<skill></command-message>\n<command-name>/cutter:<skill></command-name>")` (both branches) and, on the no-origin branch, `isMeta !== true && promptSource == null`. A scheduled line keeps its raw text, which UPS's anchored regex forces to start with `/cutter:`, so it cannot start with `<command-message>`. That holds as long as the transcript content equals the UPS prompt for unexpanded prompts. Final-round check (41c5083): `ticketOf`'s `/\s+/` split vs bash word splitting can't make the bound id differ from the script's `$2`/`$1` (all cutter scripts read the id positionally). Still open: split-pane agent-team teammates (experimental, tmux/iTerm2) are separate sessions started with a model-written spawn prompt; whether that line is `origin.kind: "human"` was not probeable. Under `--plugin-dir <repo>` the plugin's `bin/` is agent-editable, so a granted cutter script is edit→exec for the session. Both residuals (plugin-dir `bin/`, teammate/terminal-typed prompts) are documented in README's Grant bullet since ed0a74c and accepted as documented, not closed; don't re-raise them. Plugin hooks run from disk on every event, so under `--plugin-dir` in cwd an edit to any hook is edit→exec with or without grants (predates gh-53). The record in `${CLAUDE_PLUGIN_DATA}/sessions/<sid>.json` is outside cwd; a forged record = arbitrary single commands, since `*` grants are filtered only when recording. Observed origin kinds in real transcripts (2026-10): `human` (promptSource typed/queued/suggestion_accepted; prompts the coordinator types into a session are `human` too), `peer` (cross-session messages; docs say slash commands in them never run), `task-notification`, `coordinator` (wrapped "The coordinator sent a message…" text), scheduled = no origin with `turnOrigin: "scheduled"`, `claude -p`/sdk = no origin with `turnOrigin: "sdk"` (confirms since f8d274a, under the 41c5083 conditions).

Since gh-26, `.github/workflows/ci.yml` runs on `pull_request` (not `_target`), `contents: read`, no secrets, actions SHA-pinned; gates are the branch's own `.claude/cutter.json`, so CI green certifies whatever gate list the branch declares. `cutter-land merge`'s checks gate is a safety rail against merging red, not an authz boundary: its "no checks → is CI expected?" test reads the branch's workflows, so a branch can opt itself out. Judge it as fail-closed vs fail-open, not as a security boundary. Since gh-41, `cutter-land wait` only reads (advisory); `merge` re-runs the full gate, so judge `merge` alone. Its "base moved" check (exit 4) compares against `refs/remotes/origin/<base>` right after `git fetch origin +refs/heads/<base>:refs/remotes/origin/<base>`; the explicit refspec (da77ac7) updates that ref even when `remote.origin.fetch` does not cover the base (a plain `git fetch origin <base>` would leave it stale and let the check pass). `cutter-land rebase` fetches with the same refspec. GitHub has no expected-base parameter on merge, so a fetch→merge race always remains (branch protection "require up to date" closes it server-side).
